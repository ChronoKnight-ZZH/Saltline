## 3. 详细修改方案

### 3.1 `enemies/enemies.js` — `alert` 接入 `audioMask`

**改法**：在 `alert(pos, radius)` 入口乘 `(1 - clamp(audioMask, 0, 0.9))`，调用方不改。

```js
alert(pos, radius = ENEMY_TUNING.alertRadius) {
  const mask = Math.min(0.9, context.environment?.perception?.audioMask ?? 0);
  const effRadius = radius * (1 - mask);
  if (effRadius <= 0) return;
  for (const enemy of this.list) {
    // ...原遍历，距离判定把 radius 换成 effRadius
    if (distSq(enemy.pos, pos) < effRadius * effRadius) {
      enemy.mode = "investigate";
      enemy.lastKnown.copy(pos);
      context.events.emit("enemy:alert", { enemy, noise: pos });
    }
  }
}
```

**要点**：

- 只乘一次，入口处，调用方（`weapon:fire` → 45m）不改。
- 上限 `0.9`：`heavyRain` 的 `audioMask=0.72` 下 `effRadius=28%`，符合改造文档；上限防止未来某天气 `audioMask=1` 时半径归零。
- **不改事件 payload**：`enemy:alert` 保持 `{enemy, noise}`，不暴露 `radius`。
- **不加 `forceExpose`**：M3 才加，M2 加了是死代码，且会让 `check-source` 契约需要同步。

**距离判定**：若原代码用 `distanceTo`，M2 顺手换成 `distanceToSquared`（避免每敌人一次开方）；若原代码已用平方距离则不动。

### 3.2 `enemies/walker.js`（Gull，飞行）— 视觉半径接入能见度

**核心公式**：

```js
const perception = context.environment?.perception;
const vis = perception ? perception.visibility : Infinity;
const alertMul = perception ? perception.visualAlert : 1;
const effectiveRadius = Math.min(vis, baseRadius * alertMul);
```

**关键决策：区分“主动发现”与“保持交战”**

改造文档 4.4 强调“进入 `investigate` 后最短 2s”与“光柱边缘稳定”，说明状态机稳定性不能被能见度抖动破坏。M2 的原则：

| 状态转换 | 是否受 `visibility` 影响 | 理由 |
|---|---|---|
| `patrol → investigate/engage`（首次发现） | **是** | 这是能见度语义的核心：雨/夜看不远 |
| `investigate → engage`（已怀疑后确认） | **是** | 与首次一致 |
| `engage → search/investigate`（丢失目标） | **否**，用 `baseRadius` 或 `LOSE_RADIUS` | 否则玩家躲雨/进雾就脱战，破坏节奏；这是 M3 暴露系统稳定性的前置 |
| `search → patrol`（彻底丢失） | **否**，用原计时器 | 同上 |

**代码形态（以 patrol 检测为例）**：

```js
// 原（推测）
if (dist < WALKER_TUNING.sightRadius && context.physics.lineOfSight(eye, target)) {
  // 进入 investigate
}

// 改为
const perception = context.environment?.perception;
const sightBase = WALKER_TUNING.sightRadius;
const sightR = perception
  ? Math.min(perception.visibility, sightBase * perception.visualAlert)
  : sightBase;
const distSq = enemy.pos.distanceToSquared(target.pos);
if (distSq < sightR * sightR && context.physics.lineOfSight(eye, target)) {
  // 进入 investigate
}
```

**engage 中的 LOS 保持**：若原代码是 `if (!lineOfSight) → search`，**不改半径**（或改用 `baseRadius`），只在 `patrol/investigate` 的“看到玩家”判定处乘 `min`。

**每帧多次 LOS 的优化**：若原代码每帧对同一玩家多次 `lineOfSight`，M2 **不改**（留给 M6 性能调优）；只改半径来源。

**视觉检测可能是 `canSeePlayer()` 之类的 helper**：若已抽出，改 helper 内部即可；若内联，M2 顺手抽一个 `effectiveSightRadius(context)` 放在 `walker.js` 顶部：

```js
function effectiveSightRadius(context, baseRadius) {
  const p = context.environment?.perception;
  if (!p) return baseRadius;
  return Math.min(p.visibility, baseRadius * p.visualAlert);
}
```

`drone.js` 复用同样形态（各自文件内定义，不新建共享模块，避免 L3 内额外依赖）。

### 3.3 `enemies/drone.js`（Hound，地面）— 同 3.2

同 3.2 的公式与状态划分。Hound 若有“潜行/蹲下/背后偷袭”等特殊视觉规则，**M2 不改**，只改外层半径。

### 3.4 `weapons/weapon.js` — 射击扩散接入 `spreadScale`

**原则**：不改 `this.spread` 本身，只在 `fire()` 计算弹道时乘 `spreadScale`。

**若 `fire()` 用 `this.spread` 算角度**：

```js
// 原
const spread = this.spread;
// 改为
const scale = context.environment?.perception?.spreadScale ?? 1;
const spread = this.spread * scale;
```

**若 `fire()` 有 ADS / hipfire 两套 spread**：两处都乘。

**若 `spread` 是射击瞬间由公式算**：

```js
// 原
let spread = baseSpread + movingPenalty + adsBonus;
// 改为
let spread = (baseSpread + movingPenalty + adsBonus) *
  (context.environment?.perception?.spreadScale ?? 1);
```

**为什么不改 `this.spread` 本身**：

- `this.spread` 可能被 HUD 准星读取；M2 不改 HUD，改 `this.spread` 会让准星与实际弹道都变，但准星变化是 M5 的活。
- ADS 弹簧动画、视图模型摆动基于“基础扩散”，环境扩散应隐形。
- 最小改动，回滚容易。

**`context.environment` 缺失时**（fallback 有 `perception.spreadScale=1`）：`?? 1` 保证与原版一致。

### 3.5 `ui/menus.js` — 设置面板两个下拉

**3.5.1 HTML 模板**

在设置面板现有字段（画质/灵敏度/反转/音量/FOV）后追加：

```html
<div class="row">
  <label>时间</label>
  <select data-env="timeOfDay">
    <option value="dawn">黎明</option>
    <option value="noon">正午</option>
    <option value="dusk">黄昏</option>
    <option value="midnight">午夜</option>
  </select>
</div>
<div class="row">
  <label>天气</label>
  <select data-env="weather">
    <option value="clear">晴</option>
    <option value="overcast">阴</option>
    <option value="lightRain">小雨</option>
    <option value="heavyRain">大雨</option>
  </select>
</div>
```

**要点**：

- 使用 `data-env` 而非 `data-s`，与现有 settings 字段（`data-s="quality"` 等）区分，避免 `applySettings` 遍历时误取。
- 选项顺序与 `TIME_PRESETS` / `WEATHER_PRESETS` 的 `Object.keys` 一致，便于将来动态生成（M2 静态写死即可）。
- 不写 `id`，避免与现有 `input[type=range]` 的 `id` 冲突。

**3.5.2 绑定与同步**

在 `createMenus` 内构建设置面板后调用：

```js
function bindEnvSelects() {
  const timeSel = root.querySelector('select[data-env="timeOfDay"]');
  const weatherSel = root.querySelector('select[data-env="weather"]');
  if (!timeSel || !weatherSel) return;

  function syncFromEnvironment() {
    if (!context.environment) return;
    if (context.environment.timeOfDay) timeSel.value = context.environment.timeOfDay;
    if (context.environment.weather) weatherSel.value = context.environment.weather;
  }

  timeSel.addEventListener("change", () => {
    if (!context.environment) return;
    context.environment.setTimeOfDay(timeSel.value);
    context.events.emit("ui:click", {});
  });
  weatherSel.addEventListener("change", () => {
    if (!context.environment) return;
    context.environment.setWeather(weatherSel.value);
    context.events.emit("ui:click", {});
  });
  context.events.on("environment:changed", syncFromEnvironment);
  syncFromEnvironment();
}
```

**要点**：

- **从环境读，不从 settings 读**：打开面板时 `syncFromEnvironment()` 拉到当前值；用户切换后 `environment` 派发 `environment:changed`（M1 已派发），`syncFromEnvironment` 回写下拉（也覆盖“URL 参数启动后第一次打开面板”的情况）。
- **不写 settings**：`loadSettings`/`saveSettings` 不处理 `timeOfDay/weather`；`applySettings` 遍历固定字段，不碰 `data-env`。
- **取消订阅**：`context.events.on` 返回的取消函数保留在 `createMenus` 返回对象中（如 `system._offEnvironmentChanged`），原版菜单生命周期是页面级，M2 可不主动取消，但接口保留。
- **showcase / fallback**：`context.environment` 是 `FALLBACKS.environment` 时 `setTimeOfDay` 是 noop，`environment:changed` 不派发（M1 fallback 的 `setTimeOfDay` 是 noop），下拉 change 无副作用。
- **`ui:click`**：复用现有菜单点击音效，与其它设置项一致。

**3.5.3 `applySettings` 不改**

现有 `applySettings` 只遍历 `quality/sens/invertY/volume/fov`，`data-env` 不在其中，天然不写 settings。**不需要显式排除**，但建议加一行注释说明。

**3.5.4 `loadSettings` / `saveSettings` 不改**

`SETTINGS_KEY = "saltline.settings.v1"` 不变；环境状态不持久化，符合改造文档。

### 3.6 `scripts/check-source.mjs`

**M2 不改**。M2 没有新增/删除模块或导出；`alert` 签名不变、`spread` 字段不变。契约检查（M1 加的）继续覆盖 `createEnvironment / combine / applySkyPreset`。

### 3.7 `app/runtime.js`

**M2 不改**。M1 已把 `environment.update(dt)` 插在 `game.update` 之后；M2 的 `perception` 是纯查询，不需要额外更新顺序。

**暂停时是否冻结**：改造文档 4.4 说“`game:state` 非 playing 冻结暴露系统”，这是 M3/M4 的暴露系统；M2 的 `pushFrame` 在暂停时继续 damp 雨/雾/湿度是**预期行为**（画面平滑，不卡住）。M3 接暴露系统时再统一在 `environment.update` 内部按 `game.state` 判定是否跳过暴露扫描。

## 7. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 敌人视觉半径在午夜被 `visualAlert` 意外放大 | M2 `visualAlert` 恒 1；M3+ 再考虑 |
| `alert` 半径乘 mask 后，雨天开枪几乎不吸引敌人，游戏变简单 | 验收时把 `heavyRain` 的 `audioMask` 临时改 1.0 做对比；M6 调参 |
| `spread * scale` 后准星与实际弹道不匹配，手感奇怪 | M2 不改 HUD；M5 若引入准星动态大小，需同步乘 scale |
| 设置面板下拉切换时 PMREM 重烘焙卡顿 | 改造文档接受切换卡顿；`low` 下 `envBake=false` 不重烘焙；中高画质 200–400ms |
| 下拉值与 URL 参数冲突 | M2 决策：下拉 change 时立即 `set`，URL 参数只在启动时读一次；下拉不写回 URL |
| `menus.js` 在 showcase 下也被调用，下拉回调 `setTimeOfDay` 在 fallback 上是 noop | 已确认 fallback 是 noop，无副作用 |
| `engage` 中丢失目标的判定误改成受能见度影响，玩家躲雨脱战 | §3.2 明确区分“主动发现”与“保持交战”，验收清单有对应项 |

**回滚**：各文件改动独立——`enemies.js` 的乘法、`walker.js` / `drone.js` 的半径计算、`weapon.js` 的 `spreadScale`、`menus.js` 的两个下拉。任一文件回滚不影响其他；`environment.perception` 接口 M1 已稳定，M2 不新增接口。
